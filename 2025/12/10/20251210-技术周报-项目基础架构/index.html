场景管理

场景划分与切换流程

看了一眼Build只有一个_Init场景，看来后续的场景流程都是手动控制的。

_Init场景负责整个游戏的启动，简单判断了工作室LOGO动画的播放，然后再到 _Boostrap；

_Boostrap是负责初始化资源场景，目前只需要初始化单例资源场景PersistentResources，加载完后再进入_MainMenu；

然后基本的场景切换就是Primary文件夹下的几个基础场景。

场景分配思路

就如上面所提到的，Primary文件夹下的几个基础场景可以理解为“启动场景”，场景里面包括“资源加载”和“数据配置”两大核心。

  • 把场景内的资源（_Environment/ _UI）和逻辑（ _Resources）分离开来。
  • 关卡配置，比如设置背景音乐

比如正式关卡，_Resources包含GameMode和GameState脚本，mode负责资源管理，state负责游戏状态的切换和通知。另外还有单例GameInstance，用来控制关卡跳转。 _UI包含GameplayHUD脚本。

资源加载

这里主要使用AddressableResources。

加载场景资源示例。如果无法加载，则使用SceneManager。

使用Addressable的原理是，场景也被当成资源来打包，打包后的 Bundle（Addressables 的 AssetBundle）是文件，可能在本地磁盘或远端 CDN；加载时会把 Bundle 数据和所需资源读入内存；若不再需要，需要通过相应 API 减少引用或卸载才能释放内存，否则会一直占用。

如何寻找被打包的资源？

Addressables.LoadResourceLocationsAsync 的参数 key 可以是一个地址（Address）、标签（Label）、或其它键（也可以是 IResourceLocation 等）。它用于查询 Addressables 配置里匹配该键的资源条目集合。

在 Unity 编辑器中通过 Window → Asset Management → Addressables → Groups 管理：为场景条目设置 Address 字段（地址字符串）和 Labels（标签）。你传给 LoadResourceLocationsAsync 的字符串必须与某个条目的 Address 或 Label 匹配，返回的 locations 数量为 0 表示该键未被注册为 Addressable。


这样做的好处是，

  • 可用“地址”或“标签”来引用场景，便于动态加载和按需下载。
  • 可以把资源放在远端、分包、或按标签批量加载/卸载。
  • Addressables 管理依赖关系与内存生命周期，减少手动管理的错误。
  • 支持增强的发布/更新流程（不必重建整个客户端就能更新内容）。

什么是依赖关系？为什么要管理？

资源依赖（dependency）：一个场景会引用若干资源（预制体、贴图、材质、脚本able资源等），打包后这些资源会分布在一个或多个 AssetBundle 中；某些 Bundle 可能还会引用其他 Bundle（共享资源），这就是依赖关系。

Addressables 的行为：当你用 Addressables.LoadSceneAsync 加载场景时，Addressables 会根据 Catalog 自动解析并加载该场景对应的 Bundle 以及它依赖的所有 Bundle（无需你手动列出或加载每个 Bundle）。

引用计数（reference counting）：Addressables/ResourceManager 为每个加载的资源/Bundle 维护引用计数（通过 AsyncOperationHandle 组合管理）。每次通过 Addressables 加载，会增加对应资源和依赖 Bundle 的计数；调用 Addressables.UnloadSceneAsync 或 Addressables.Release(handle) 会减少计数。只有当计数降到 0 时，资源或 Bundle 才真正被卸载并释放内存。

为什么重要：有引用计数能避免重复加载同一个共享 Bundle（节省内存和 IO），并防止在某个场景仍在使用共享资源时被错误卸载；如果不用 Addressables，你需要自己管理依赖关系和计数，容易出错导致重复加载或内存泄漏。

对比 SceneManager.LoadSceneAsync：SceneManager 只负责把场景内容加入层次，并不自动处理 AssetBundle 的依赖加载和引用计数；如果你的资源走 AssetBundle/Addressables 流程，应优先用 Addressables，以便自动管理依赖与释放。

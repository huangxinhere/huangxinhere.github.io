知识整理-Job System

发表于2025-12-14|更新于2026-11-11|游戏开发UnityDOTS
|浏览量:

多线程回顾

CPU（中央处理器）

物理硬件，真正“执行指令”的地方。

一个CPU有多个核心（Core），一个核心在同一时刻只能执行一个线程。

性能上限 = 你同时能让多少个 CPU 核心在干活。

操作系统层：线程与调度

线程（Thread）

操作系统调度的最小执行单位，本质是一段可被 CPU 执行的指令流。

线程包括：栈、寄存器上下文、调度状态。

线程 ≠ CPU，是被调度到CPU 核心上运行的，可以被运行、挂起和切换。

线程调度（OS Scheduler）

操作系统负责哪个线程 在什么时候 跑在哪个核心上。

如时间片轮转、抢占式，对 Unity / C# 完全透明。

Unity总体线程模型

Unity主线程（Main Thread）

是Unity 引擎的“唯一权威线程”，所有引擎状态在这里是安全的。

执行的主要任务有Update / FixedUpdate、操作 GameObject / Transform、渲染、物理、动画等。绝大多数 Unity API 只能在主线程调用。

但不能做高强度计算（会卡帧）和长时间阻塞（Sleep / 等待）。

Unity的工作线程池（Worker Threads）

是Unity启动时创建的一组后台线程，数量通常 ≈ CPU 核心数 - 1。

用于执行 Unity 内部并行任务，或者执行 Job System 的 Job。

生命周期由 Unity 管理，不允许直接访问 UnityEngine API。

C# 层：Thread / Task / async

C# Thread

对 OS 线程的直接封装。

真线程；需要自己管理生命周期，无法识别Unity的帧/生命周期，所以易错和出问题。

Task 与线程池（.NET）

Task是一个“可能异步完成的工作描述”，不等于线程。可能用线程，也可能不用线程（I/O）。

线程池是.NET 维护的一组通用线程，为 Task.Run 等服务。它不理解Unity的帧概念，会和主线程抢CPU。

async / await

一种“非阻塞的流程控制机制”。把方法编译成状态机，一遇到await，保存“方法执行状态”，让当前线程继续干别的。

误区：不创建线程、不保证并行、不提升计算性能。

await的流程分析：

阶段 发生的事
执行到 await 保存方法状态机
当前线程 立刻释放执行权
等待期间 无线程被阻塞
完成后 continuation 被投递
继续执行 跑在“被安排的线程”

Unity + async 的特殊性

UnitySynchronizationContext是Unity 安装的同步上下文，为了强制 async continuation 回到主线程。

所以async 看起来“能改 Transform”，但本质仍然不是并行。

async在 Unity 中的适用与缺点

异步适用于 网络、存档、登录、资源加载（非计算）。这些任务的特点是慢，但不吃CPU。

缺点：不加速CPU计算、生命周期与 GameObject 脱节、线程池不可控、不可异步。


并发/并行 & 异步/同步

  • 同步（Synchronous）：调用方发出请求后，必须“等到结果返回”，在此期间，调用方不能继续自己的逻辑。【阻塞当前执行流】
  • 异步（Asynchronous）：调用方发出请求后，不必等待结果，可以先继续执行其它逻辑，结果在“将来某个时间点”再处理。【不阻塞当前执行流】

异步描述的是“等待方式”，不是“线程模型”。


  • 并行：单任务并行（Data-level parallelism），把一件事拆成很多“一样的小事”并行做。
  • 并发：多任务并发（Task-level parallelism），同时处理“不同的事情”。

用一个最小模型区分四种概念：

  1. 同步+单线程
  1. 异步+单线程

仍然只有一条线程。但等待期间线程没有阻塞，通过“回调/状态机”实现。

这是大多数 async/await 的真实形态。

  1. 同步+多线程

A阻塞了，但系统总体还能动。

  1. 异步+多线程

同时存在同步和异步，常见于CPU密集任务。

Unity Job System

是Unity 官方的、面向 CPU 并行计算的系统。用来把“可并行的纯计算工作”安全、高效地分发到多核 CPU 上执行，同时与 Unity 的主线程和帧系统严格对齐。

使用 Unity 的工作线程池、明确的调度点、帧级可控、从机制上禁止 Unity API。

解决的问题

Unity是主线程引擎，而现代CPU是多核架构，传统MonoBehaviour 只能吃 1 个核心。结果就是主线程爆满，其它CPU核心大量闲置。

对于Thread/Task的缺点，上文已分析过，Unity API 非线程安全、其生命周期与帧系统脱节、线程池与引擎无协同、性能不可预测。

构成部分

可以理解成，Unity 在主线程和 CPU 核心之间，加了一层“可控的并行调度器”。

Job（工作单元）

Job是一个“不可访问 Unity API 的、纯计算任务描述”。

通常是一个struct、实现某个Job接口、只操作数据，不操作世界。

数据（Native Containers）

普通C#数据比如List<T>/class有GC、引用、不可预测、非线程安全。

所以Job System只允许使用“可被静态分析的数据结构”，如NativeArray、NativeList、NativeHashMap<K, V>以及其他 Native 容器。特点是只存在于 非托管内存，无GC，连续内存，可被多线程安全分析。

调度与依赖（Schedule / JobHandle）

把这个 Job 放进 Unity 的调度系统，等合适的时候执行。


而JobHandle代表了Job的依赖关系。

代码例子是“B依赖A”，Unity 的调度器会在 Worker Threads 空闲时自动尽早执行A，A完成后立刻执行B。在这里不需要把Job依赖理解为“控制流”，而要当成“数据流”，也就是数据什么时候可用，而不是代码什么时候跑。


如果用频繁Complete来取代依赖关系的处理，会导致主线程频繁阻塞。但是用依赖串联的话能够最大化并行，最后统一Complete。

工作原理

以某一帧执行为例，

  • 主线程准备数据：创建NativeArray，填充输入数据。
  • 主线程调度Job：创建Job struct，调用Schedule()。这时Job 被放入 Job Queue，主线程不阻塞，继续执行后续逻辑。
  • Worker Threads 并行执行：多个核心同时跑，Unity 自动拆分工作量，不需要关心线程数量。
  • 同步点（Complete）：主线程等待所有相关 Job 完成，确保数据一致性，然后可以使用结果。
  • 主线程使用结果：读取NativeArray，更新GameObject / Transform。

硬约束

  • Job 内不能访问 UnityEngine API。
  • Job 必须是 struct。struct是值类型并且可复制，无引用语义，更容易并行分析。
  • 数据访问必须声明，例如[ReadOnly]、[WriteOnly]，让Unity做静态安全分析（Safety System），防止写出数据竞争。

与Burst的关系

Burst是一个专门为 Job 编译代码的高性能编译器，Job System 不依赖 Burst，但不配 Burst 等于浪费。它可以自动向量化、使用 SIMD、消除冗余、生成极快的机器码。

适用情况

非常适合

  • 大量同构计算
  • 可拆分循环
  • 数学 / 几何 / AI / 路径
  • 数据驱动逻辑

不适合

  • 少量逻辑
  • 强顺序依赖
  • UI
  • 动画状态机
  • 直接操作 GameObject

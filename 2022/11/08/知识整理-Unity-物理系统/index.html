物理引擎的工作

每次刷新的时候，物理引擎会按顺序执行四个主要步骤：

  1. 构建某种空间数据结构，以实现高效的“相交测试 intersection tests”。相交测试检查两个物理对象的几何形状是否接触或重叠。
  2. 检测碰撞，并根据所有接触或重叠的物理对象之间的接触点生成约束constraints。
  3. 运行物理“求解器” the physics “solver” 根据物体的约束条件和其他因素（如质量、重力、摩擦力）来更新物理物体的速度。
  4. 根据新的速度移动物理物体。

在游戏代码中，物理引擎构建的空间数据结构 the spatial data structure 也可以用于各种游戏逻辑。例如，当开枪时，游戏代码可以查询空间结构来确定子弹在其路径上可能击中什么。


【FixedUpdate的帧率】

由于帧之间的时间差通常变化，并且物理模拟不一定需要与渲染或游戏模拟以相同的速率更新，因此物理模拟通常以自己的固定更新速率进行更新。

这是通过每帧 0 次或多次更新物理模拟来近似平均速率实现的。

例如，一帧可能执行 0 次物理更新，而下一帧可能执行 3 次，再下一帧只执行 1 次，等等，目的是随着时间的推移平均化，以匹配预期的物理更新速率。


Rigidbodies 刚体

在大多数游戏物理引擎中，物理对象通常是刚体，这意味着它们是具有均匀分布质量的固体对象，不会弯曲、挤压或以任何方式改变形状。这与软体（如橡胶等可变形物体）、流体、气体以及像沙子一样的颗粒不同。

通常，每个刚体对象的数据包括这些元素：

  • position 位置
  • orientation 方向
  • collider (the geometry used in collision detection)
    碰撞体（用于碰撞检测的几何形状）
  • linear velocity (direction and speed of travel)
    线性速度（运动方向和速度）
  • angular velocity (direction and speed of rotation)
    角速度（旋转方向和速度）
  • mass 质量
  • center of mass (a point, usually inside the object)
    质心（一个点，通常在物体内部）
  • inertia tensor (the rotational semi-equivalent of mass)
    惯性张量（旋转的半等效质量）

…以及其他可选元素：

  • linear and angular damping (decay of velocities)
    线性和角阻尼（速度衰减）
  • gravity (per-object override of the global gravity)
    重力（每个对象的局部重力覆盖）
  • friction coefficient 摩擦系数
  • restitution (bounciness) 恢复系数（弹性）
  • collision filters 碰撞过滤器

【为什么有Rigidbody？】

Transform组件控制物体的位置旋转和缩放，同样也控制着其他组件。

而collider因为物理碰撞的原因会自动改变Transform的参数；这个改变Transform的过程就需要物理引擎(physics engine)来操作，因此物理引擎需要一个方法来完成这个任务。所以——刚体Rigidbody就用来移动和连接Collider。


Dynamic

一个动态刚体是一个“普通”的刚体物理对象，这意味着它受重力影响，并受到其碰撞产生的力的作用。

在某些物理引擎中，长时间静止的动态物体可能会被“置于休眠状态”，这可以通过在模拟的某些阶段跳过其处理来提高性能。

例如，落到地面并停止运动的对象，一旦其动量降至零（或接近零），就会进入休眠状态。处于休眠状态的物体会受到力的作用时重新激活，例如被其他物体撞击时。

Unity 的 Havok Physics 会对静止物体进行休眠处理，但 Unity 物理引擎本身没有这个功能：在 Unity 物理引擎中，物体始终是完全活跃的。


Kinematic

运动学体是一个具有概念上无限质量刚体。因此，其变换和速度不会自动受到与其他刚体碰撞或其他交互的影响。相反，用户自己的代码负责设置运动学体的变换和速度，以控制其运动方式。

根据维基百科，“运动学是物理学和数学的一个分支，在经典力学中发展，描述了点、物体和物体系统（物体组）的运动，而不考虑使它们运动的力。”因此，在物理引擎中，“运动学”一词适用于没有（自动）施加力的物体。


当希望一个移动的物体在与其他物体碰撞时影响它们，但该物体本身不自动对这些碰撞或其他物理属性（例如重力、摩擦或阻尼）做出反应时，运动学体就很有用。

例如，电梯应该移动其楼层上静止的物体，因此需要将其设置为物理物体；然而，您通常希望严格在自己的代码中控制电梯的运动，而不是让电梯被障碍物卡住或受重力影响，因此您应该将电梯设置为运动学体。


Colliders 碰撞体

Unity Physics 支持以下碰撞体形状：

  • Box-盒体：由长度、高度和宽度定义的长方体。
  • Sphere-球体：由半径定义的球体。
  • Capsule-胶囊体：具有圆形两端的圆柱体，由一条内线段和半径定义。
  • Cylinder-圆柱体：由高度和半径定义的圆柱体。
  • Triangle / Quad-三角形/四边形：由 3 个或 4 个共面的顶点形成的三角形或四边形。
  • Convex hulls-凸包：由一组 3D 点定义的任意凸包。
  • Mesh-网格：由三角形和四边形组成的网格。
  • Compound-复合体：由多个碰撞器形状组合而成。
  • Terrain-地形：由高度样本组成的均匀网格。

Static

静态碰撞器是一个具有碰撞器但没有速度、质量或其他动态体属性的对象。通常，构成游戏环境的对象，如静态道具、地板、墙壁或地形，应该是静态碰撞器。

物理引擎不会检查静态碰撞体之间的碰撞。

在 Unity 物理中，可以在运行时移动静态碰撞器，但这样做会触发用于碰撞检测的静态碰撞器边界体积层次结构的昂贵重建。通常应该避免移动静态碰撞器。对于偶尔移动的碰撞器，可以考虑使用速度为 0 的运动学体。


碰撞查询

在代码中，询问物理引擎诸如“如果这个物体移动到这个位置或朝这个方向移动，它会撞到什么？”或“如果从这里朝这个方向发射，这个投射物会撞到什么？”等问题通常很有用。这类问题被称为碰撞查询。

Unity 物理 API 提供了五种类型的碰撞查询：

  • Overlap query-重叠查询：查找所有其包围盒与给定形状重叠的碰撞器。
  • Ray cast query-射线投射查询：查找任意碰撞体与给定射线（一条有向线段）之间的交点（如果存在）。
  • Collider cast query -碰撞体投射查询（又名“形状投射”或“扫描”）：查找碰撞体与沿给定线段移动的给定形状之间的交点（如果存在）。
  • Collider distance query-碰撞体距离查询：在给定最大半径范围内，查找连接给定形状与每个碰撞体的最短线段。
  • Point distance query-点距离查询：在给定的最大半径范围内，找到连接给定点和每个碰撞体的最短线段。

【碰撞检测的广相和窄相 broad phase and narrow phases】

因为确定哪些物理体对会相互碰撞可能相当昂贵，碰撞检测通常分为两个阶段：

  1. 第一个阶段称为“粗”阶段，物理引擎找到其轴对齐包围盒**（AABB）相交**的碰撞器。AABB 是一个与世界轴对齐（换句话说，一个未旋转的盒子）并完全包围对象的盒子。
  2. 第二个阶段称为“细”阶段，检查在粗阶段中 AABB 相交的对象对，看它们的实际碰撞器是否相交。

因为 AABB 相交测试单独都很便宜（尤其是与包围体和网格相交测试相比），将碰撞检测分为粗和细阶段通常会减少碰撞检测所需的成对相交测试数量。

广义阶段也常常通过将碰撞体的 AABB 分组到某种空间结构中（如八叉树 octree 或边界体积层次结构（Bounding Volume Hierarchy, BVH））来进一步加速，从而使得广义阶段只需检查同一世界部分中的 AABB 之间的交集。


八叉树是一种树形数据结构，每个内部节点都正好有八个子节点。八叉树常用于分割三维空间，将其递归细分为八个卦限。八叉树是四叉树在三维空间中的对应，在三维图形、三维游戏引擎等领域有很多应用。


**包围体层次结构（BVH）**是一组几何对象上的树形结构。所有构成树叶节点的几何对象都被包裹在边界体积中。这些节点随后被分组为小集合，并封装在更大的边界体积内。这些体积再以递归方式被分组并封装在其他更大的边界体积内，最终形成一个在树顶只有一个边界体积的树形结构。包围体层次结构用于高效支持对几何对象集合的多种操作，例如在碰撞检测和光线追踪中。


Unity 物理为动态刚体和运动学创建一个 BVH，并且为静态碰撞器创建一个额外的 BVH。

碰撞和触发事件

对于物理对象之间的检测到的碰撞，物理引擎可能会生成包含碰撞信息的碰撞事件。

由于为每次碰撞触发事件可能会非常昂贵，物理引擎通常只会为用户指定的事件触发体触发碰撞事件。

Joints & Motors 约束

除了物理引擎的碰撞检测生成的接触约束外，有时可能希望手动创建一些可以永久持续的额外约束。例如，可能希望将两个物体连接在一起，使它们在移动时相互拖拽。这种两个物体之间的持久约束称为关节 Joints。

根据关节的配置，其约束可能会限制某些自由度（degree of freedom，DoF），例如，一个关节可能只允许两个物体沿单一轴进行相对旋转。

Unity Physics 提供了几种类型的关节：

  • Ball and Socket-球窝关节：允许围绕无限多个轴进行运动。人类在髋部和肩部有这样的关节。
  • Limited Hinge-有限铰链：允许在一个轴上有限的运动。人类的手指和膝盖上有这种关节。
  • Fixed-固定：将两个刚体连接在一起，使其无法独立于彼此移动。
  • Hinge-铰链：允许在一个轴上自由旋转。可用于旋转车轮和转盘。
  • Prismatic-滑动副：将两个刚体约束在一个轴上的滑动运动。可用于制作各种滑动门。
  • Ragdoll-布娃娃：限制在几个轴上的运动。适用于创建角色。
  • Stiff Spring-刚性弹簧：将两个物体约束在彼此一定距离之外。

一个 motor 是一种关节的变体，具有“驱动”约束，这意味着一种在两个物体原本静止时仍会对其施加力的约束。

Unity Physics 提供几种电机：

  • Rotation Motor-旋转电机：一个围绕轴旋转至目标角度的电动铰链关节。
  • Angular Velocity Motor-角速度电机：一个围绕轴以恒定目标速度旋转的电动铰链关节。
  • Position Motor-位置电机：一个驱动至相对目标位置的电动滑动关节。
  • Linear Velocity Motor-线性速度电机：一种驱动至相对目标位置并以恒定目标速度运动的棱柱关节电机。

关于Rigidbody和Collider

  • Rigidbody继承了Transform所以可以Update位置和旋转。
  • 同一个游戏对象（以及子物体）所有的Collider2D都隐式地与其Rigidbody连接。也就是说Collider会跟着Rigidbody移动。（现在回想到移动物体都是用rb的方法，从来没有Collider的移动方法可调用，现在可以理解了）所以凡是Collider的移动都不能通过Transform或者它的位移等等，只能通过Rigidbody，这样才能确保其运动符合真实的物理情况。而连接同一个Rigidbody的Collider则不会发生碰撞。
  • 只有Collider可以碰撞，Rigidbody不能。

  • 任何一个Collider默认和绑定的Rigidbody的BodyType一致（或着理解为继承）。

  • 这个参数改变时，一些质量相关的内部参数就要被重新计算，所有相关Collider和Rigidbody的联系也要在下一个FixedUpdate重新计算。

连续碰撞检测（CCD）

连续碰撞检测 (CCD) - Unity 手册

扫掠式CCD

  • 通过扫掠对象的前向轨迹来计算对象的潜在碰撞（采用对象的当前速度）；
  • 如果沿对象移动方向有接触，该算法会计算撞击时间并移动对象直至达到该时间。
  • 此方法依赖于线性扫掠，所以会忽略物体的角运动，这在对象迅速旋转时会引起穿隧效应。
  • 此方法的另一个问题是性能问题。如果附近有大量启用 CCD 的高速对象，CCD 的开销将由于进行额外的扫掠而很快增加，因此物理引擎不得不执行更多的 CCD 子步骤。

推断性CCD

  • 基于对象的线性运动和角运动增大一个对象的粗筛阶段轴对齐最小包围盒 (AABB)。该算法是一种推测性的算法，因为会选取下一物理步骤中的所有潜在触点。然后将所有触点送入解算器，因此可确保满足所有的触点约束，使对象不会穿过任何碰撞。
  • 可能的问题：幽灵碰撞；穿隧

总体思路

为了解决Update和FixedUpdate不同步的问题，（rigidbody必须要在FixedUpdate之中，而用户输入又必须在UpdateUnity为什么推荐在FixedUpdate处理物理模拟？ - 知乎 (zhihu.com)），那么在Update刷新率不同的情况下，如何确保FixedUpdate中的rb移动是完全一致呢？

  • Update触发FixedUpdate及时响应的问题：如果是GetButton，那么由于Update刷新不同，FixedUpdate处理的时间可能多，也可能少（假如按下了0.1s，刷新快的Update就已经刷新了10帧，慢的刷新一帧，但是由于FixedUpdate是得看Update的响应的，所以刷新了10帧的FixedUpdate也跟着刷新了8帧，慢的FixedUpdate只跟着刷新了1帧【只做粗略估计，不严谨计算】）；如果是GetButtonDown（倘若设布尔状态值的其实和上一点差不多），响应可能会不太准，试过按下之后跳不起来的情况。因为是按下那一帧设为true然后下一帧重置为false，如果FixedUpdate刚好错过，那么就没有响应了。
  • 一般来说解决方法是，Update设置布尔值来保存这个状态，直到FixedUpdate接收并执行就取消这个记录的状态。记录是否触发还好，但是要记录长按短按呢？如果要确保每个电脑执行效果都一样的话，这就变得有些棘手。
    • 一种解决办法是跳跃初始的速度、力都是固定的，短按就使加速度往下来使人物立马往下。这样的话FixedUpdate相当于触发一次就行。如果控制力：物体质量和施加力能确保相同，只是力作用时间不同才会导致效果不同；那么要用瞬间冲击力Impulse。长按中断的时候得施加往下的力？【对于力没有研究得很清楚，当前帧施加了力，那么那个瞬间有个加速度，同时受到重力的影响，在合力的作用下逐帧运动……？】对于力和速度到底用哪个好，我初步地比较了一下，力要改变速度是要经过加速度这个过程的，比如中断长按，如果突然加往下的力，那一帧加速度变大，速度可能恰好停止、小有上升、最不乐观的是猛下落一截【还没有亲身实践，根据小学物理猜测。】所以很明显控制力对最终速度的影响并不直观【还有什么代价？】。F= ma,m=1,F=a,v=v0+atv=v0+av=v0+F,质量为1的时候倒是能理解成和速度有直接关系。而直接控制速度的话就少了m的约束。
  • 官方的例子就是控制速度（以后找到力的例子也好好研究研究），控制速度也有不方便的地方，如果受到力的作用，也不得不考虑所有力的可能性然后计算合加速度，这对于碰撞来说是非常麻烦的。官方例子直接把Rigidbody设置为Kinematic，只受速度的影响。由此，漫长的看代码痛苦过程就开始了……【完全陌生的领域啊啊啊啊（习惯用力控制的萌新）】

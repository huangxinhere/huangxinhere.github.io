为什么有ECS

  • CPU架构的演进

早期（~2010 年前）CPU性能主要靠更高主频和更复杂的单核流水线，可简单理解为“只要代码顺序执行，CPU 会越来越快”，这正是 OOP / GameObject 架构诞生时的前提。

但由于功耗墙、制程极限等原因，单核增长几乎停滞。

而性能的突破来自于多核、SIMD、Cache命中率。


  • OOP（面向对象）架构的局限

直觉模型：

对象是中心，数据 + 行为混在一起；通过“引用”访问其他对象。这在人类理解层面非常友好。

但是对于CPU来说，

当 CPU 执行 player.weapon.Fire() 时：跳到 Player——跳到 Weapon——再跳到 Weapon 内的数据；大量内存跳转会导致Cache 频繁失效、CPU 空转等待数据。

另外，1000个对象执行1000次Update的时候，每个Update的逻辑不同，导致分支多、指令不可预测、很难并行，不能充分发挥多核CPU的优势。


  • ECS解决的问题

ECS的第一原则是：

CPU 关心的是数据，不是对象。

因此ECS反直觉的设计是：

  1. 对象（Entity）不存数据
  2. 组件只存数据
  3. 行为集中批量处理

而且在内存中是这样的：

CPU执行时，

因此总结来说就是：

OOP / GameObject ECS / Entities
内存访问 随机 连续
Update 分散 集中
并行 困难 天然
Cache 低命中 高命中
规模 数百 数万

Unity为什么要设计ECS

先从结构来看，GameObject的本质模型：

对象（Object）是中心，行为附着在对象上，Update分散在每个对象里；

组件 = 数据 + 逻辑 + 生命周期。

这样导致可控性很低：

问题 本质
Update 数量爆炸 行为分散
Cache Miss 多 数据不连续
GC 难避免 引用对象
多线程困难 Unity Object 线程不安全
批处理困难 逻辑耦合

当对象规模上千时，问题呈指数级放大。

对于Unity来说，现有的GameObject设计已然难以满足大规模单位（RTS）、DOTS多线程、数据驱动工具链等情况，在性能维度上很容易输给Unreal/自研引擎。因此Unity采取的策略是提供第二套设计：Entities。


👉那为什么Unreal的性能好？

表面看起来Unreal的模型也是Actor+组件，有生命周期Tick()。

它的优势不是ECS，而是在OOP框架内做了极端优化：

  • C++（零 GC）：没有托管 GC，内存生命周期可控。
  • 手写内存管理：对象池、紧凑布局、自定义 allocator。
  • Tick 分组与调度：TickGroup、TickDependency、显式控制顺序。
  • 更少的“脚本级 Update”：强烈反对每 Actor Tick、推崇集中逻辑。

UE没有彻底ECS的原因在于完全 ECS 对设计师不友好，而且C++ 项目迁移成本极高，Blueprint 生态依赖 Actor。


Unity Entities

Entity的整体结构图

Entity

不存数据、逻辑，不参与运算，唯一的职责是标识一行数据。


为了通过 ID 查找实体，世界中的 EntityManager 维护一个实体元数据数组。

实体的索引（Index）表示它在该元数据数组中的槽位，该槽位存储指向存储该实体的 chunk 的指针，以及实体在该 chunk 中的索引。

实体版本号允许在实体被销毁后重用实体索引：当实体被销毁时，其索引处存储的版本号会递增。

因此如果某个 ID 的版本号与索引处存储的版本号不匹配，那么该 ID 必定指向一个已经被销毁的实体，或者可能从未存在过。


Component

结构体，不能包含任何托管字段类型，无行为逻辑；这样就可以连续存储、 SIMD、Job 化、无 GC。不是“组件脚本”，而是“数据字段集合”。


EntityManager

世界中的实体通过其实体管理器进行创建、销毁和修改。


Archetype 原型

拥有完全相同组件集合的一组 Entity 的结构定义。

这样设计的目的是，让“经常一起访问的数据”物理上也放在一起。

实际上，添加或移除实体的组件会改变实体所属的原型，这需要 EntityManager 实际上将实体移动到新的原型中。

即使一个原型中所有的实体都被移除，该原型也不会被销毁，直到其世界被销毁。


Chunk 区块

一个原型中的实体存储在属于该原型的 16KiB 内存块中，称为区块。每个区块最多存储 128 个实体。数据连续；Cache 命中率极高。

对比GameObject：

GameObject ECS
transform 在堆上 LocalTransform 在 Chunk
指针跳转 顺序访问
cache miss cache hit

每个实体的 ID 和每种类型的组件都存储在块各自的独立数组中。例如，在具有 A 和 B 组件类型的实体的原型中，每个块将存储三个数组：

  • 一个用于实体 ID 的数组
  • 一个用于 A 组件的数组
  • 以及一个用于 B 组件的数组

该块中第一个实体的 ID 和组件存储在这些数组的索引 0 处，第二个实体存储在索引 1 处，第三个实体存储在索引 2 处，以此类推。

一个块的数组总是紧密排列的：

  • 当一个新的实体被添加到块中时，它会被存储在数组中第一个空闲的索引处
  • 当实体从块中移除时（这发生在实体被销毁或被移动到另一个原型时），块中最后一个实体会被移动来填补这个空位

块（chunk）的创建和销毁由 EntityManager 处理：

  • 当实体被添加到一个原型（archetype）中，而该原型已有的块（chunk）都已满时，EntityManager 才会创建一个新的块（chunk）
  • EntityManager 只在块的最后一个实体被移除时销毁块（chunk）

任何向块（chunk）内添加、移除或移动实体的 EntityManager 操作都称为结构变更。此类变更只能在主线程上进行，而不能在Job。


Query

EntityQuery 能够高效地查找所有具有指定组件类型的实体。

例如，如果查询查找所有具有组件类型 A 和 B 的实体，那么查询将收集包含 A 和 B 的所有原型块，而不管这些原型可能具有的其他组件类型。

匹配查询的原型将缓存，直到向世界添加新的原型为止。由于世界中的现有原型集在程序生命周期的早期往往会稳定下来，因此这种缓存通常有助于使查询成本大大降低。


System

系统是一个属于实体世界的代码单元，它在主线程上运行（通常每帧运行一次）。定义何时/处理哪些数据，如何处理。

通常，系统只会访问它自己的世界中的实体，但这并不是一个强制的限制。

系统被定义为实现 ISystem 接口的结构体，它包含三个关键方法：

World

世界是一组实体的集合。实体的 ID 编号仅在其所属世界中唯一。

世界还拥有一组系统，这些是运行在主线程上的代码单元，通常每帧运行一次。一个世界中的实体通常仅被该世界的系统及其调度的工作所访问（但这并非强制限制）。

通常用于Game World/Simulation World/Test World/Server World等，适合无场景模拟或多世界并行。

ECS工作流

创建子场景

将 GameObject 和 MonoBehaviour 组件添加到子场景中，而 baker 会将 GameObject 和 MonoBehaviour 组件转换为实体和 ECS 组件。

创建ECS组件

在创建组件之前，应该考虑组件将存储哪种类型的数据以及将在什么上下文中使用它。

然后，可以决定使用哪种组件类型来实现该组件。

创建实体

要在编辑器中创建实体，将 GameObject 添加到子场景中。烘焙过程将这些 GameObject 转换为实体。

如果要将 ECS 组件附加到转换后的实体：

  • 创建 authoring component，实际上是 MonoBehaviour 组件，用于存储从编辑器传递给 ECS 组件的值。
  • 一个baker将 ECS 组件附加到实体上，并将authoring component中的值填充到 ECS 组件中。

创建系统

系统创建应用程序中的行为。

为此，它们可以查询和转换 ECS 组件数据，创建和销毁实体，以及向实体添加和移除 ECS 组件。默认情况下，当你创建一个系统时，Unity 会实例化它并将其添加到默认世界。

优化系统

默认情况下，在系统中编写的任何代码都在主线程上同步运行。

如果系统影响多个实体的数据并且可以从多线程中受益，最佳实践是创建与 Burst 兼容的工作，并在可能的情况下将它们调度为并行运行。Burst 将 C#代码编译为优化的原生 CPU 代码，而Job能够将工作分配到多个线程并利用多个处理器。

比如使用IJobEntity，将Job调度到多个线程上并行运行。回顾Job System，Job单元存储了数据和执行逻辑，并通过Schedule方法由Unity放入Job Queue并由Worker Threads并行执行。这里就要考虑如何将Entity和Components与Job兼容。使用 IJobEntity 会改变查询和迭代组件数据的方式，并改变实例化新实体的方式。

Unity 只能在主线程上创建实体，这意味着并行作业必须使用Entity Command Buffer来记录创建和配置新实体的命令。并行作业运行后，Unity 在主线程上播放实体命令缓冲区，以实际创建和配置实体。

例：使用IJobEntity构建Job；数据又被封装到Job里面，不过是通过函数传参直接传入计算，通过EntityCommandBuffer来记录实体操作命令

系统直接创建和安排Job。组件Spawner是如何被传入每个Job的？

如果一个系统工作量不大，例如它只处理少量实体的组件数据，那么并行调度工作的开销可能会超过多线程带来的性能提升。

Unity-动画系统

发表于2026-02-05|更新于2026-11-11|游戏开发Unity动画
|浏览量:

动画系统概述

本质上是时间驱动的姿态求解系统。

动画系统 = 在给定时间t、控制参数C、约束条件K下，求解角色当前姿态 Pose(t)。


姿态生成 Pose Generator

Pose

动画系统的核心不是 Clip，而是 Pose Buffer：

Pose = 当前帧 每个骨骼的局部 / 模型空间变换

这也是为什么IK可以叠加在动画之后、Layer可以“覆盖”、Mask可以“过滤骨骼”。所有动画系统，本质都是在做Pose的组合与修改。


Animation Clip

从引擎视角看，Animation Clip = 一组随时间变化的通道函数。

它是只读数据，不关系“角色状态”“为什么播放”等上层状态。


状态机

状态机是控制流系统。解决的不是“动画播放”，而是在连续时间轴上，选择哪个Pose生成器在主导。本质上是一个带条件的、时间连续的Pose选择器。

比如每个state ≈ 一个Pose Generator，Transition ≈ 一个权重随时间变化的混合函数。


然而在复杂状态下，状态机会出现Transition越来越难控、动画卡死/错切/状态回退等问题。根本原因是它用离散决策模型去逼近一个连续、高维、耦合的运动问题，因此模型并不匹配。具体而言，**经典有限状态机（FSM）**的数学模型是：

  • 一时刻 ∈ 某个离散状态 Si

  • 状态之间通过条件触发跳转

  • 同一时间只存在一个“主状态”

这意味着FSM隐含了三个前提假设：

  1. 世界是可分割的（Idle/Walk/Run/Jump）
  2. 任意时刻只属于一个状态
  3. 状态之间的边界是清晰的

但真实的角色运动在数学上更像：

  • 状态是一个连续变量：x = [速度, 加速度, 朝向, 角速度, 接触状态, 意图, …]
  • 动画是这个状态空间中的一条轨迹
  • 每一帧都在相邻轨迹之间滑动

所以FSM把连续空间强行切块导致的后果是：

【状态爆炸】

比如走 + 转向、走 + 转向 + 攻击、走 + 受击、跑 + 上坡 + 左转，FSM唯一手段是拆成更多离散状态。

【边界不稳定】

FSM的切换发生在一个离散时间点，或者一个布尔条件触发。但运动是连续的，于是会发生切换抖动、卡在中间态、动画没播完就被打断等问题。

而Transition Blend只在状态边界做平滑，不改变状态机的离散本质。

所以结论是，状态机只能做粗粒度决策，不能承担运动逻辑。


那么要用什么技术来解决这个问题？核心思想是，不再用“状态”描述运动，而用“参数空间 / 特征空间”描述运动。


【Blend Tree】

混合树，Pose = f(parameters)，其中parameters是连续的（可以设置根据速度/方向/角度）。但是它仍然假设动画结构是人为设计的，还需要FSM来选择哪个Blend Tree。所以Blend Tree是FSM的局部替代，还不是根本替代。


【Motion Matching】

把当前角色状态等同于一个高维特征向量，动画库则等于一堆特征向量，每帧动画就是找最近邻；这样就直接消除了状态边界。相当于从逻辑控制改成数据驱动搜索。

这给予的一个启发是，Data-Driven Animation的统一思想就是：

用连续空间的几何关系，替代离散逻辑判断。


姿态融合 Pose Compositor

Blend

Blend 的目标不是“平滑”，而是当多个系统都想控制角色时，如何得到一个“合理姿态”。比如移动系统想控制腿，攻击系统想控制上半身，IK 想控制手等，这就导致Layer、Mask、Additive、Override等出现。

其中，Additive 的地位非常高，本质是 Final Pose = Base Pose + Delta Pose，可以减少动画数量、提高复用率、支持细粒度增加（呼吸、抖动、后坐力）。


Layer / Mask

这两者解决的是控制权问题。

从系统视角看，Layer=优先级，Mask=作用域。这是一个并发控制系统的问题：多个子系统并行地产生Pose，谁说了算？


姿态修正 Pose Modifier

IK / 约束系统

IK 的引入，意味着一个质变：动画不再完全由数据决定，而是由“目标 + 约束”决定。相当于从“离线作者” → “运行时求解”；从“动画师主导” → “系统主导”。


蒙皮/渲染 Skinning / Render

骨骼动画

用一组有层级关系的变换矩阵，去驱动网格顶点的形变。

动画系统负责：算骨骼姿态，骨骼动画负责：把姿态作用到网格。

骨骼动画在整个动画系统的职责在于：

系统 负责什么
Animator / Anim Graph 决定每个骨骼“应该是什么姿态”
骨骼系统 把姿态转成矩阵
Skinning 把矩阵作用到顶点
GPU 真正算顶点位置

核心挑战

可拓展性

常见灾难：

  • 新需求要加 10 个 State
  • 动画逻辑和代码强耦合
  • 不同角色无法复用系统

成熟项目的方向：

  • 动画系统“数据驱动”
  • 程序只喂参数，不写流程

性能与并行化

现代动画系统要考虑：

  • 骨骼数量
  • IK 次数
  • Blend 次数
  • 多角色并行

未来趋势

  • 从 State Machine → Data-Driven

Motion Matching

Pose Search

Trajectory-Based Animation

核心思想：

不用“状态”描述运动，用“特征空间”匹配运动

  • 从 Animation → Animation + Simulation

动画提供“意图”

物理 / 稳定器提供“结果修正”

比如：

  • Procedural animation
  • Physics-based IK
  • Hybrid Ragdoll
  • 从工具导向 → 系统导向

未来动画系统更像：

  • 一个“姿态求解框架”
  • 而不是“动画播放器”
